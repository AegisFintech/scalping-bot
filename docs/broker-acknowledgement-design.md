# Prospective broker acknowledgement evidence — design in progress

Issue [#407](https://github.com/AegisFintech/scalping-bot/issues/407) tracks capture for future callbacks. No capture or migration is active. Existing historical acknowledgements cannot be reconstructed.

The client parses the JSON callback into `BrokerExecution`, preserving optional order fields. `normalizeDemoExecution` then computes the existing 1.1 event hash from a narrower projection. `PostgresDemoExecutionStore.persist` uses that hash and event key for idempotency, immutable variants and reconciliation. Adding fields to that hash would change existing identity and can manufacture conflicts. History reconstruction is a different source from a broker callback.

The [cTrader order model](https://github.com/spotware/openapi-proto-messages/blob/main/OpenApiModelMessages.proto) declares `stopPrice`, `slippageInPoints`, `timeInForce` and `expirationTimestamp` optional. Capture presence explicitly; do not substitute request values or protobuf defaults for omitted JSON fields. The order update timestamp is distinct from callback receipt and database persistence. Pip/tick/volume, fees and FX are separate sources and require their own observation times; an order callback alone does not prove they were contemporaneous.

A compatible design must preserve the old hash and every existing duplicate/conflict path. An additive, independently hashed evidence record can retain allowlisted callback fields and all three clocks. A later reconciliation observation cannot be labeled as the original callback. Same old event identity with different captured fields must retain variants, not overwrite either version. Missing callbacks and interrupted writes remain unknown; neither a flat account nor elapsed time repairs that gap.

Open engineering decision: coupling an optional research write to the journal transaction can turn an evidence-storage outage into an execution gate, while writing afterward can lose the callback between commits. The implementation must explicitly test and document its chosen failure and recovery behavior before claiming full retention. The evidence must not create a broker command, change trade decisions, replay an unknown outcome or silently erase failures. Schema, reader privileges, bounded export, migration, recovery and rollback must be reviewed together.

## Chosen direction for implementation

For a validated strategy-owned `ORDER_ACCEPTED` callback, project only the explicitly present, validated order terms. Keep the callback source and its receipt clock alongside a separate evidence digest. Insert this evidence in the **same** database transaction as the existing event, including the existing-event and conflict branches. Reference the retained event by its existing account-scoped identity; retain distinct evidence digests as distinct immutable variants. The write must happen for duplicate callbacks too, because the old event digest does not cover the new fields. Never attach unverified broker-derived values to an older reconstructed event as though they were its original callback.

The transaction supplies a database persistence time separately from the broker's optional order-update time and local callback receive time. It must not pretend that `now()` is a precise commit clock or that received time proves when the broker first sent the event. Read-only exports report both values and any conflicts, absence, ordering ambiguity and truncation explicitly. A callback lost before durable commit stays unknown; there is no backfill or attempt to replay a broker command.

A database failure rolls back the existing event and evidence together and uses the recorder's existing durable-persistence failure path. This retains the current fail-closed storage policy but adds a new evidence write that can itself fail and trigger that policy; it is an operational behavior and latency cost that integration tests must verify. Missing or malformed optional evidence must be represented as unavailable or rejected **as evidence** without inventing fields or blocking an otherwise valid broker event. Exact handling must avoid logging raw payloads or credentials. The migration is additive with no historical backfill; rollback disables the writer and retains the table. Research reader grants must be SELECT-only and scoped.

The implementation must verify callback origin, strategy ownership, field ranges and precision; exercise duplicate callbacks with matching and differing fields, early transaction exits, database rollback, restart/recovery and immutable prior event hashes; and compare exports against the actual recorded source. Actual pip/tick/volume/cost/FX facts may be attached only from independently timestamped evidence with an explicitly justified temporal relationship. This design is not a promise that those facts exist or that every callback is available.
